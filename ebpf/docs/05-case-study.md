# 05 案例分析：一次内存泄漏的自动处置全程

> 本文用真实运行记录复盘：一个"看似正常"的多线程服务如何在 10 秒内
> 被 eBPF tracker 完成检测 → 抓栈 → 归因 → 处置。
> 完整报告原件见 [assets/sample_leak_report.md](assets/sample_leak_report.md)。

## 1. 场景

`demos/leak_demo` 模拟一个多线程服务，三条代码路径：

- `handle_http_request`：HTTP 请求处理，"缓存"请求体但从不淘汰
  （**快速泄漏，约 8MB/s**）；
- `handle_ws_connection`：WebSocket 会话接入，会话表插入失败路径漏
  free（**慢速泄漏，约 0.3MB/s**）；
- `handle_health_check`：健康检查，正常分配/释放（**对照路径**）。

运维视角的表象只有一个："这进程 RSS 一直在涨"。涨的是哪条路径？
传统手段要么上 valgrind/ASan（性能不可用于生产），要么重启加日志
（周期长、未必复现）。

## 2. 处置过程（真实记录）

```bash
sudo python3 src/tracker.py --comm leak_demo --rss-t1 30 --rss-t2 55 --rss-interval 0.5
./demos/leak_demo
```

tracker 输出：

```
00:15:13.676 [target] 开始跟踪 pid=157783 comm=leak_demo
00:15:13.766 [THRESH-1] pid=157783 comm=leak_demo RSS=38.7MB >= 30MB，开始抓取用户态堆栈
00:15:15.785 [THRESH-2] pid=157783 comm=leak_demo RSS=56.1MB >= 55MB，生成泄漏报告...
00:15:15.788 [ACTION] 已 SIGKILL pid=157783。报告: reports/leak_report_leak_demo_157783_20260812_001515.md
```

从越线到处置完毕 **3 毫秒**（报告生成在进程存活期内完成，随后才 kill）。

## 3. 报告解读（真实输出节选）

```
## Top 10 泄漏堆栈
按用户态页错误采样数排序（采样率 1/1，每采样约对应 4KB 的 RSS 增长）。共采样 4454 次。

### #1  采样 4225 次（约 16.5MB，占 94.9%）
libc.so.6+0x1a8653
parse_request_body+0x27 [leak_demo]
handle_http_request+0x1c [leak_demo]
http_worker+0x15 [leak_demo]
...

### #2  采样 151 次（约 0.6MB，占 3.4%）
libc.so.6+0x1a8653
handle_ws_connection+0xd [leak_demo]
ws_worker+0x15 [leak_demo]
...

### #3  采样 67 次（约 0.3MB，占 1.5%）
libc.so.6+0xb1321
libc.so.6+0xb3317
libc.so.6+0xb3f6d
cache_store_entry+0x1e [leak_demo]
parse_request_body+0x27 [leak_demo]
...
```

三个观察：

1. **归因正确**：#1（94.9%）是 HTTP 路径，#2（3.4%）是 WebSocket 路径。
   占比 94.9% : 3.4% 与两条路径的真实泄漏速率比（8MB/s : 0.3MB/s
   ≈ 96.4% : 3.6%）几乎一致——因为归因单位是"页错误"，每次页错误
   ≈ 4KB 实际驻留，**占比就是各路径对 RSS 增长的贡献占比**。
2. **栈顶是 `libc.so.6+0x...` 而不是 `memset`**：泄漏点
   `cache_store_entry` 在 #1 里"丢"了——帧指针链在 glibc 的 memset
   内部断掉（glibc 无帧指针）。#3 恰好是同一泄漏点在 malloc 路径上的
   完整栈。这展示了帧指针栈行走的固有局限：业务代码帧齐全，穿过
   libc 的帧可能缺失，但**定位到业务函数已足够**。
3. **对照路径（健康检查）没有出现在榜上**：它分配后立刻释放，页被
   复用不产生净增长，自然没有页错误归因——这正是"按页错误归因"
   优于"按 malloc 计数归因"的地方：malloc 计数会把健康检查也算成
   "高频申请者"造成误报。

## 4. 为什么阈值 2 才杀，而不是阈值 1 就杀

阈值 1（T1）是"关注线"：可能是正常增长，也可能是泄漏，代价是打开
抓栈（armed，有性能开销，需采样率控制）。阈值 2（T2）是"行动线"：
持续增长到 T2 才确认异常，此时堆栈证据已攒够，先固化证据再处置。
两阈值之间的时间窗就是**证据采集窗**——窗口长度由泄漏速率和阈值
间距决定，本例约 2 秒、攒了 4454 次采样。

参数经验：

- T1 设为"历史稳态 RSS 的 1.5 倍左右"，避免误 armed；
- T2 - T1 的间距按泄漏速率估：保证窗口内能攒 ≥ 几千次采样
  （采样率 1/1）或相应调高采样；
- 生产环境建议配 `--no-kill` 先运行一段时间观察报告质量，再放开
  自动处置。

## 5. 同案延伸：如果伴随 D 态或锁问题

泄漏进程在处置前的运行期，tracker 同步记录的 D 态/等锁事件会一并
写入报告"关联事件"节。例如若泄漏路径在锁内分配（持锁分配大内存），
报告中会同时出现 `LOCK-HOLD` 事件——单份报告即可拼出"谁拿着锁、
在哪条路径、涨了多少内存"的完整现场。

## 6. 复盘：这套机制的边界

- 抓的是 **RSS 增长**的归因，对"分配但不触碰"的虚拟内存膨胀不敏感
  （那种泄漏通常也不致命）；
- 对**短时突发后自行回落**的波动不处置（秒级轮询+双阈值天然过滤）；
- 若进程在 armed 后崩溃，maps 消失则无法符号化——报告的成败系于
  "符号化先于 kill"这个顺序约束（已在流程中硬保证）。
